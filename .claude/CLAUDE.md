## Working rules

- **Greenfield**: no data needs keeping. Change code, contract, config keys and documents in place; no compatibility layers, shims or
  deprecations. The one exception is the store (P-89): the Cantara database is kept, so its schema changes only by an additive migration
  (`internal/store/migrations/`), with a copy taken first.
  Commit to `main` locally only (Conventional Commits, a few per feature, not one per step) and never push `main`. When a feature is
  complete, open one PR for it (its commits pushed to a branch); CI runs once, on the PR. When the owner explicitly asks to commit and push
  directly, push `main` itself (no branch, no PR): his instruction wins, for that request. Between changes run only the tests of what
  changed; the full `make check` once, before the PR. Never rerun a flaky job: fix the test. CI runs quick checks only; the browser tests and the load and size checks run locally in `make check` (P-85).
- **The agent drives the work, goal first.** Getting it done is the north star. Every piece of work starts by writing its goal, its
  acceptance criteria (observable, checkable) and its definition of done (code, tests, the full gate green, documents and the code map
  current, PR open and CI green) in the design note or the `plan.md` row; then the agent carries it out alone, to the end, and starts the
  next milestone when the last is done. The specs cover what the owner wants; the owner accepts the agent's choices. A missing detail is
  decided (the most conventional, safest option), recorded in `decisions.md` and carried on with; the agent never asks the owner for
  input, clarification or confirmation, leaves no open questions in documents or replies, and stops only for what it cannot do itself
  (a release or tag, a secret, a real-world account) or what the rules forbid; those are named once in the final report with the exact
  step left. Reports state what is done, how it was verified and what remains unverified, in a few lines.
- **Version**: semantic versioning (P-16): `v2.0.0` first, then every release bumps the patch version unless the owner decides a minor
  or major bump; the agent does not tag releases. Published tags are never moved.
- **Read-only towards GitHub** (P-71): read permissions, GET requests and GraphQL queries only, never a write or a mutation; the fake
  GitHub fails a test on anything else. A feature that needs another permission or event adds its row to `internal/prereq.Needs`
  and to the documentation's table in the same commit (`TestPrerequisitesDocumented`).
- **Data lives in SQLite; memory only loads it** (owner, P-97): every new piece of data the portal keeps is a row in the store, written through before it is acknowledged, loaded into memory at the start for fast reads. An instance that dies must come back with everything it had acknowledged (a hard requirement, proved by `make rehearse`). Keep it simple.
- **The repo stays deployment-neutral** (owner): no company, host or customer name anywhere in it, commit messages and PR text included; such facts go to the dossier. `scripts/check-neutral.sh` (the commit hooks and `make check`) refuses the names listed in a private file outside the repo.
- **No Hazelcast, Redis or Postgres in any new work** (owner, repeated): no design, feature, test run, rehearsal or verification item rests on them, and they are never listed as unverified. The existing `internal/cluster` code stays as it is until the owner says otherwise; the Hazelcast container commands below are not run. Search stays in memory; the store is SQLite.
- Keep it small: no package, config key, metric or dependency before the code that needs it. Avoid over-engineering.
- Dependencies are the latest releases of the best-in-class choice (owner P-17), pure Go on the server; `bluemonday` is the one exception
  (`plan.md` section 3). Web: TypeScript 7 is `tsc` (`@typescript/native`); the `typescript` name holds the 6.0 API for typescript-eslint and Next.js.
- Planning and design live under `.claude/work/` and hold only what is built and in progress; finished work moves to `.claude/work/history/`; `docs/` is user documentation only.
- Commits: Conventional Commits, no AI attribution lines. Generated files are never edited by hand (`make gen`).
- No test touches the network: loopback only, `internal/github/githubtest` and recorded fixtures.
- Keep this file current: update it in the same commit when the state, layout or rules change.

## Architecture in brief

One static Go binary (`CGO_ENABLED=0`) that serves the API and supervises the Next.js web UI server (`web/bundle`, run with Node on
loopback; every page is proxied through Go). GitHub feeds sync jobs (on the leader when several instances share a
Hazelcast cluster; the others apply its outcomes); jobs write SQLite (the one place data lives; memory only loads it) and
publish an immutable snapshot behind an atomic pointer; request handlers read only the snapshot. Features never import features; wiring
only in `cmd/scp`. Untrusted bytes pass through bounded parsers and one sanitiser producing `SafeHTML`. Public port `:9090`, admin `:9091`.
