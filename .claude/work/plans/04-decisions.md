## 1. Principles

1. **Package by feature, not by layer.** Each feature package owns its domain types, use-cases, HTTP handlers, templates and tests. No `controllers/`, `services/`, `models/` buckets.
2. **Clean boundaries.** Dependencies point inward/downward only. Features talk through small interfaces defined by the *consumer* (accept interfaces, return structs). No feature imports another feature's internals. Cross-feature data flows through the read model (snapshot) or explicit narrow interfaces. Enforce with `internal/` and an import-boundary test (e.g. `go list`-based or `depguard`/`go-arch-lint`).
3. **SRP.** One reason to change per package. Fetching, parsing, rendering, storing and presenting are different packages/roles.
4. **Composition root only in `cmd/scp`.** Explicit constructor wiring, no DI framework, no globals, no `init()` side effects.
5. **Stdlib first.** `net/http` (1.22+ ServeMux patterns), `log/slog`, `html/template`, `encoding/json`, `context`, `embed`, `errors`. Third-party only where it clearly earns its place (see the research results in `05-research/`).
6. **Correct by construction over defensive checking.** Typed IDs, typed errors, `Secret` type, sanitised-HTML type, immutable snapshots, validated config.
7. **Failure is a first-class state.** Every fetched item has freshness and status. Stale-while-error. Readiness is defined.
8. **Observable and testable.** Structured logs, OpenTelemetry metrics/traces, fake GitHub server and recorded fixtures, no network in tests, `-race`, golden files.
9. **Design guardrails are binding.** [`02-design-guardrails.md`](02-design-guardrails.md) (GR-01 to GR-45) applies to every decision, ADR and unit design.
10. **LLM-friendly surface.** Content and APIs are designed to be consumed by humans and LLM agents alike (see D-06).

## 4. Architecture decisions (binding; the architecture document elaborates)

- **D-01 Module and layout.** One Go module (path assumption: `github.com/cantara/source-code-portal`, change freely). `cmd/scp` (composition root + CLI subcommands `serve`, `config lint`, `version`). Everything else under `internal/`. Feature packages under `internal/` (not layered buckets), plus a small `internal/platform/*` set of cross-cutting infra packages (config, logging, telemetry, httpserver, secret, clock).
- **D-02 Read model + store.** Serving state is an immutable `Snapshot` behind `atomic.Pointer`, built by the sync engine. Durable last-good state in embedded SQLite (CGO-free driver, WAL) behind a narrow `Store` interface; never on the request path. bbolt is the documented alternative; Redis/Valkey out of scope. Optional small TTL cache (otter) only if profiling justifies it. (Confirm driver/version in research.)
- **D-03 Sync engine.** One feature package (`sync`) owns scheduling, keyed coalescing job queue, per-upstream concurrency limits, jittered backoff, rate-limit pause, readiness gating. Features register *jobs*; the engine does not know GitHub specifics.
- **D-04 GitHub boundary.** A `github` adapter package owns the HTTP client, auth, ETag/conditional requests, pagination, rate-limit handling, circuit breaker, typed errors, and webhook payload types. Other features depend on small consumer-side interfaces implemented by it.
- **D-05 Web (the rendering, template, asset and live-update parts are SUPERSEDED by D-16; the HTTP server, middleware chain, single-source route table concept, and public/admin listener split stand).** `net/http` ServeMux, middleware chain (request id, recover, access log, security headers incl. CSP, gzip where useful, timeouts). `html/template` (or templ if research favours it) with embedded templates; self-hosted assets with content hashes; HTMX (vendored) for the live panel; a **named route table** is the only source of URLs (templates and redirects), guarded by a link-crawl test. Separate public and admin listeners.
- **D-06 Documentation format (LLM-compliant).**
  - Source of truth: `README.md` (CommonMark + GFM: tables, task lists, strikethrough, autolinks, footnotes, GitHub alerts `> [!NOTE]`).
  - Optional **YAML front matter** and an optional repository-level descriptor (working name `.scp.yaml` or `scp.yaml`) that carries structured semantics Markdown lacks: title, summary, owners/team, lifecycle (experimental/active/deprecated), tags, links (runbook, dashboards, API spec), docs ordering/navigation, and per-repo overrides for integrations. The research task decides the exact schema, whether to adopt an existing convention (for example Backstage `catalog-info.yaml` fields, `llms.txt`, OpenAPI/AsyncAPI pointers) rather than invent, and how to represent rich blocks (diagrams via Mermaid fenced blocks rendered client-side or server-side, admonitions via GFM alerts) so that raw source stays readable to LLMs.
  - Rendering: goldmark + GFM + chroma + front-matter extraction, then bluemonday sanitising into a distinct `SafeHTML` type; relative link/image rewriting to GitHub raw/blob or to portal routes; content addressed by blob SHA.
  - LLM surface: the portal serves `GET /llms.txt` and `/llms-full.txt` (index of groups/repos/docs), and raw Markdown for each doc at a `.md` URL (`/repos/{repo}/readme.md`) with front matter and structured metadata as JSON (`/api/v1/...` read-only, stable, versioned). Sitemap and `robots.txt` configurable.
- **D-07 Configuration.** One typed, versioned config (YAML), env overrides (`SCP_` prefix), `*_FILE` secrets, flags; strict decoding (unknown key = error); `Validate()`; documented keys == consumed keys (generated reference + test); embedded default; JSON Schema generated for IDE support and `scp config lint`.
- **D-08 Observability.** `slog` JSON; OpenTelemetry metrics+traces (otelhttp server and client transport), Prometheus on admin listener (and/or OTLP); `/livez`, `/readyz` public, `/status`, `/metrics`, `/debug/pprof` admin only.
- **D-09 Security.** Secrets typed and redacted; webhook HMAC-SHA256 on raw body, constant-time, size limit, delivery-id dedupe; CSP + security headers; sanitised content; SSRF guard on any configurable outbound URL (Jenkins, GHES) with allow-list; non-root, read-only filesystem container.
- **D-10 Testing.** Unit + table tests; `httptest` fake GitHub (recorded fixtures); golden files for HTML, badges, config lint reports; `-race`; fuzz for matcher, config, renderer; route-crawl test; `goleak`; import-boundary test; end-to-end smoke test that boots the binary against the fake GitHub and waits for `/readyz`.
- **D-11 Delivery.** `CGO_ENABLED=0`, `-trimpath`, static binary, distroless:nonroot image by digest, build info via ldflags, GitHub Actions CI (vet, staticcheck/golangci-lint, test -race, govulncheck, build, image, smoke), Renovate/Dependabot, cosign signing optional.
- **D-12 Routes (canonical).**
  `GET /` -> redirect `/dashboard`; `GET /dashboard`; `GET /groups/{groupId}`; `GET /groups/{groupId}/commits`; `GET /commits`; `GET /repos/{repo}` (docs); `GET /repos/{repo}/commits`; `GET /repos/{repo}/readme.md`; `GET /badges/{repo}/{kind}.svg`; `GET /pages/{slug}`; `GET /llms.txt`; `GET /api/v1/...`; `POST /webhooks/github`; `GET /livez`, `GET /readyz`; static under `/assets/{hash}/...`. Admin listener: `/status`, `/metrics`, `/debug/pprof/`.
  Repository identifier is the repo *name* within the configured organisation (single-org by design; multi-org is a documented extension via `org/repo` form).
- **D-13 Organisations (REVISED by D-17).** The catalogue models *sources* (a GitHub org/user account via an App installation or token), so one or many organisations are supported by configuration; a single-org deployment is simply one source. Repository identity is `source/org/repo`; routes may omit the org when exactly one org is configured.
- **D-17 Source integration: GitHub App first, flexible by design (owner directive 2026-10-13).**
  - **GitHub App is the recommended and default-documented integration**, because it is least-privilege (read-only permissions chosen per data need), installation-scoped (access = exactly the repositories the org admin selects, which is also the safest visibility policy), short-lived tokens (1 h installation tokens minted from the App private key, no long-lived user secret), has higher and scaling rate limits, and delivers webhooks to one App endpoint with installation lifecycle events (`installation`, `installation_repositories`) that make repository discovery event-driven. Repository discovery therefore prefers `GET /installation/repositories` over `GET /orgs/{org}/repos`.
  - **Flexibility is a requirement, not an afterthought.** Integration is split into two orthogonal, pluggable concerns behind small consumer-side interfaces in the `github` adapter (and `catalog` for sources):
    1. **Credential strategy (`TokenSource`):** `github_app` (App ID + private key from file/env/secret manager, installation id auto-discovered or pinned, token cache with early refresh, per-installation rate-limit state), `fine_grained_pat` / `pat`, `oauth_user_token` (optional, for user-scoped access), `anonymous` (public data, very low limits, dev only), and `token_command`/external provider hook for secret-manager setups. Strategy chosen by config; startup validation proves the credential works and reports the effective permissions and visible repositories; private key material never logged (typed `Secret`).
    2. **Acquisition mode (`SourceReader`):** `api` (default: REST, optional GraphQL batching), `webhook-assisted` (default overlay: events enqueue refresh), and an **optional `git` mode** for cases the API handles poorly (very large monorepo manifests discovery, private mirrors, non-GitHub hosts): shallow/sparse partial clone using go-git or the git binary into a bounded cache directory, with strict timeouts, size limits and no hook/config execution. `git` mode is specified in the design but off by default; research decides go-git vs git binary. The rest of SCP depends only on the `SourceReader`/`TokenSource` interfaces and the normalised model, never on how bytes were obtained.
  - **Hosts:** configurable API/web/upload base URLs per source so GitHub Enterprise Server and GitHub Enterprise Cloud with data residency work; proxy and custom CA support; SSRF allow-list applies. Other providers (GitLab, Bitbucket, Gitea) are *not* in scope but the interfaces must not leak GitHub-specific types into feature packages (a `scm` model: Repository, Ref, Commit, Tree, Blob, Release, WebhookEvent).
  - **Onboarding and operations:** `scp github app manifest` (or documented) flow using the GitHub App Manifest flow to generate an App with the minimal permission set; a `scp doctor` command that checks credentials, permissions, webhook reachability and rate-limit state; a health/status view of installations (account, repo count, last sync, rate limit remaining/reset, token expiry); graceful handling of installation suspension, removal and permission changes (repos disappear cleanly from the snapshot, nothing crashes, a clear status is shown).
  - **Webhooks:** with an App, webhook secret and endpoint are configured once on the App; SCP verifies `X-Hub-Signature-256`, routes by `installation.id`, and also supports plain organisation/repository webhooks for PAT mode. Both feed the same sync jobs (D-03).
  - **Visibility policy:** `public_only` (default), `installation_scope` (everything the App/token can see; requires auth mode D-16/`access` for the UI per Q-03), with startup validation refusing to publish private repositories without access control.
  - **Rate limits and budget:** per-credential (per-installation) limiter and breaker in the adapter; ETag persistence; budget arithmetic per D-09 research; GraphQL optional for discovery batching.
- **D-14 Repository hygiene.** README, CHANGELOG, ADRs, `docs/`; CI as the quality gate; no committed generated assets; `llms.txt` generated by the app and also checked into the repo as `llms.txt` pointing to docs for agents working on the repo.

- **D-16 Frontend: React + shadcn/ui + TypeScript SPA (owner directive 2026-10-13; supersedes server-rendered `html/template` + HTMX in D-05, and the "no Node" statement in D-11).** The owner briefly considered Svelte 5 but has decided on React; Svelte 5 is recorded as a considered alternative in an ADR with a short, evidence-based comparison, not as an open question.
  - **Stack (research verifies versions/maintenance):** React (current stable major) + TypeScript `strict` + Vite + Tailwind CSS (current major) + shadcn/ui components (copied into the repo, built on Radix UI/Base UI primitives) + a typed router and server-state library (candidates TanStack Router + TanStack Query vs React Router; research recommends one) + Zod for runtime validation at the API boundary + lucide icons (self-hosted, tree-shaken). pnpm, Node pinned via `.nvmrc`/`engines`. **Node is a build-time tool only; the runtime is the single static Go binary.** Tests: Vitest + Testing Library + MSW (or equivalent) for units/components, Playwright (+ axe) for e2e and accessibility, Storybook optional (research decides). Lint/format: ESLint flat config + Prettier or Biome (research decides).
  - **Delivery:** `web/` holds the SPA. `pnpm build` -> `web/dist`, embedded via `//go:embed` in a small Go package that serves it with: SPA history fallback to `index.html` (never for `/api`, `/badges`, `/llms.txt`, `/webhooks`, etc.), content-hashed immutable assets, `index.html` `no-cache`, precompressed variants, strict CSP with no third-party origins (inline theme pre-paint handled with a hash/nonce injected by Go or moved to a small external script). Dev: Vite dev server proxying `/api` to the Go server. CI builds the frontend before the Go build; the Go build also works with a committed-nothing-generated policy (`web/dist` is built in CI/Docker, a tiny placeholder is embedded for `go test`).
  - **API-first contract:** all UI data comes from the versioned JSON API (`/api/v1`). The **OpenAPI 3.1 document is the source of truth** (contract-first, `api/openapi.yaml`), Go handlers are verified against it by contract tests (and/or generated strict-server stubs; research decides), and the TypeScript client and types are generated from it (no hand-written fetch types). Errors use RFC 9457 problem details. Pagination, ETag/conditional GET, and field naming conventions are fixed in the architecture. The JSON API is also the LLM-facing structured surface (D-06), so it is a product feature, not a UI detail.
  - **Documentation rendering:** the backend remains the *single* Markdown pipeline (goldmark + chroma + bluemonday -> `SafeHTML`, table of contents, front matter, link/image rewriting) and returns sanitised HTML plus structured metadata over the API; the SPA displays it inside a typography component (shadcn/Tailwind typography styles). No client-side parsing of untrusted Markdown; DOMPurify as defence in depth only if research recommends it. Mermaid, if supported, is rendered client-side from fenced blocks under CSP-safe configuration.
  - **Badges** remain server-rendered SVG endpoints (`/badges/...`) because external READMEs embed them; the SPA uses the same URLs.
  - **LLM/crawler surface is server-generated, not SPA-dependent:** `/llms.txt`, `/llms-full.txt`, per-doc raw `.md`, JSON API, sitemap. The research evaluates whether minimal server-side meta/prerender for shareable links (Open Graph for repo/group pages) is worth it; default is no SSR.
  - **Live updates:** TanStack Query-style cache with polling+ETag or SSE (research decides), visibility-aware, with an explicit staleness indicator from the API's freshness fields.
  - **Frontend organisation mirrors the backend: package-by-feature** (`web/src/features/{dashboard,groups,commits,docs,manifests,pages,status}/...`, shared `web/src/components/ui` for shadcn, `web/src/lib/{api,routes,format}`), feature-sliced import rules enforced by lint (`eslint-plugin-boundaries` or equivalent). Routes are typed; no hard-coded URL strings (replaces the Go route-table crawl test with a typed-route + link e2e test).
  - **Quality bars:** WCAG 2.2 AA, keyboard-first, dark/light theming via shadcn CSS variables with `prefers-color-scheme` and persisted override, responsive down to 360 px, i18n-ready strings (English now), bundle budget (research proposes numbers), Lighthouse CI/axe in CI.
  - **Effect on Go packages:** `internal/ui` is replaced by `internal/webapp` (embedded SPA hosting only) and a shared `internal/httpapi` (problem details, pagination, ETag, auth context, OpenAPI contract tests). Each feature package owns its own API handlers (`api.go`) and DTOs, not controllers/templates.
- **D-15 Package manifest intelligence (N-01).** SCP parses package-manager data for all major languages. Binding principles; the research task `07-manifest-parsing` and the design fill in specifics:
  - **Ecosystems (minimum set):** Maven (pom.xml, incl. parent/properties/dependencyManagement/BOM, modules), Gradle (build.gradle(.kts), settings, version catalogs `libs.versions.toml`, lockfiles), npm/yarn/pnpm/bun (package.json + lockfiles), Python (pyproject.toml PEP 621/Poetry/uv, requirements*.txt, Pipfile, setup.cfg, poetry.lock/uv.lock), Go (go.mod, go.sum, go.work), Rust (Cargo.toml/lock), .NET (csproj/fsproj/vbproj, Directory.Packages.props, packages.config, packages.lock.json), Ruby (Gemfile/.gemspec/lock), PHP (composer.json/lock), Swift (Package.swift/Package.resolved), Dart/Flutter (pubspec), Elixir (mix.exs/lock), CocoaPods, Kotlin via Gradle, plus container/IaC where cheap (Dockerfile FROM, GitHub Actions `uses:`, Terraform providers). New ecosystems are added by implementing one interface and registering it, with no change to other packages (open/closed).
  - **Build vs adopt:** evaluate adopting existing Go libraries (for example google/osv-scalibr extractors, the OSV lockfile parsers, anchore/syft catalogers, CycloneDX/SPDX tooling, `package-url/packageurl-go`, `golang.org/x/mod` for go.mod, `BurntSushi/toml`/pelletier toml, a Maven POM library) versus own parsers. Rules: static parsing only, **never execute build tools or untrusted code**; no network at parse time except through the GitHub adapter; bounded input size and parse time (fuzzed); deterministic and pure functions of file bytes.
  - **Identity and model:** Package URL (purl) is the identity; normalised `Manifest`/`Component`/`Dependency` types (ecosystem, name, namespace, version or constraint, scope: runtime/dev/test/build/optional, direct vs transitive when a lockfile exists, source file and location, licence if declared), plus repo-level facts (declared name/version of the repo's own artifacts, language(s), build tool, module layout). Import/export of CycloneDX and SPDX is a boundary format, not the internal model.
  - **Acquisition:** discover manifest files through the GitHub Git Trees API (recursive, truncation-aware) with a configurable path allow-list, fetch changed files conditionally by blob SHA; evaluate the GitHub dependency-graph SBOM endpoint as an additional/fallback source and its coverage/limits. Refresh is driven by the sync engine and push webhooks that touch manifest paths. Content is addressed by blob SHA, so unchanged files are never re-parsed.
  - **Consumers (why it exists):** repository page "Technology & dependencies" panel; org-wide *internal* dependency graph (repo A depends on artifact produced by repo B, matched by purl against artifacts the catalogue's repos declare), reverse-dependency ("used by") view, version spread/outdated-ness view where a version source is available, licence summary, group-level rollups, JSON API and `llms.txt`/LLM outputs, badges (for example "language", "latest version"), and optional metrics. Vulnerability data (OSV) is an optional later provider, not v1.
  - **Boundaries:** `manifests` owns parsing, model and graph computation; it does not fetch from GitHub itself (consumes an interface implemented by `github`), does not render HTML (exposes view models consumed by `ui`/feature views), and publishes results into the snapshot like every other feature.
